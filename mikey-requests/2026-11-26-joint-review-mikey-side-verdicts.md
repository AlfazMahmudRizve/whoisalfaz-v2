## H8 (G-F1) — AI training scrapers allow/block

**Verdict: PROCEED-WITH-CONDITIONS — ALLOW is the right call, once the conditions are met.**

**Reasoning.** The contradiction itself is the defect: robots.txt explicitly `Allow: /` for GPTBot, ClaudeBot, ChatGPT-User, anthropic-ai, Amazonbot, while the edge returns 403 "Access Denied" (`Server: cloudflare`) to those user-agents (G-F1). Either consistent position beats a published Allow contradicted by a live block. Nothing in the evidence shows proprietary IP at risk — the site is 108 public blog posts plus marketing/service pages, no unpublished or paywalled content identified. The concrete, evidenced harm from the current block is to ChatGPT-User, which is user-triggered browsing, not training — blocking it breaks "browse this site for me" requests. The search-citation bots that actually drive AI answers (OAI-SearchBot, Claude-SearchBot, PerplexityBot, Google-Extended, Googlebot, Applebot, bingbot, DuckAssistBot) already return 200 with full HTML, so allowing training bots adds nothing to live citability and blocking them removes nothing from it — the decision is about training use and policy coherence, not search visibility. The GEO benefit of training access is asserted, not measured (geo-agentic.md: no paid-tool citation measurement, platform scores qualitative only); no citation-rate gain is claimed here. Downstream dependency is real: G-F4 Content-Signal/RSL cannot be written until this policy is stated.

**Conditions before any edge change.** (1) Sheriff confirms the ALLOW policy — his content/IP call, not a technical one. (2) Draken names the Cloudflare rule/layer returning the 403 (rule ID and name — Bot Fight Mode / Super Bot Fight Mode / managed ruleset / custom WAF rule) from Security Events/WAF logs, and confirms whether verified bots are affected at all. (3) Re-probe using OpenAI/Anthropic published verified-bot IP ranges (or reverse-DNS verification) from a clean network — not the audit VM's datacenter IP. The 403 evidence is thin: probes carried bot UA strings from a datacenter IP "without verified-bot IP ranges, so this is behaviour toward unverified traffic, not proof the real verified bots are blocked" (G-F1). It is possible verified bots already pass and only spoofed UAs are blocked. (4) Any skip rule must be verified-bot-only (Cloudflare verified-bot check), never a blanket UA-string allow — a UA allow is trivially spoofed. (5) Keep CCBot and Bytespider blocked — their 403 matches their robots.txt `Disallow: /`. (6) After the change, re-probe each agent and confirm 200 (GPTBot, ClaudeBot, ChatGPT-User, Amazonbot), record the rule ID changed, then write G-F4 (Content-Signal + security.txt; RSL only once the licensing choice is made). (7) Correction to Draken's gate wording: his question lumps in Google-Extended, but the evidence shows Google-Extended already returns 200 (G-F1 table) — it is not part of the live conflict.

**Risks.** Of ALLOW: training use of public content without attribution or compensation — bounded, since the content is already public and indexed; reversible by a robots.txt flip + removing the skip rule. Of BLOCK (or leaving the contradiction): continued policy incoherence, user-triggered ChatGPT browsing stays broken, G-F4 stays unwritable. Of acting without conditions 2–3: changing Cloudflare rules on VM-only probe data risks disabling a rule that is actually working correctly against impersonators.

**Question for Draken's side.** Which Cloudflare rule (rule ID and name) is returning the 403 to GPTBot/ClaudeBot/ChatGPT-User/Amazonbot, and do your Cloudflare Security Events logs show any requests from *verified* GPTBot/ClaudeBot IPs being blocked, or only unverified/datacenter-IP traffic? Can you confirm from the dashboard whether verified AI bots already pass, and who owns editing robots.txt (Vercel or Cloudflare) so the policy and the edge can be changed together?

## H6 (P-F1) — TTFB re-measure before code changes

**Verdict: PROCEED — "re-measure first, no code changes yet" is the right sequence, and H6 as written (diagnose, then decide) should go ahead as stated.**

**Reasoning.** All TTFB numbers come from one biased instrument: curl from the audit VM only, with ~0.65–0.90 s of TLS/proxy overhead on every request (baseline: example.com total 1.51 s, TLS 0.65 s) — the "worst-case server TTFB ~2 s+" figure is derived by subtracting that estimated overhead, so absolute values are estimates, not measurements. The finding is instability, not steady slowness: `/partners/` 0.70–3.25 s, `/audit/` 1.68–2.08 s, homepage 0.67–1.77 s, all on `x-vercel-cache: HIT` with `Age: ~85,000 s` (P-F1). A 2–3× spread on cache HITs means the cause is intermittent (revalidation timing, routing, or the Cloudflare→Vercel hop), and no code change can be targeted until the variable is isolated. No corroborating performance data exists: no Lighthouse/PSI scores (PSI rate-limited on the shared keyless quota), no CrUX field data, no LCP/CLS/INP numbers; only 6 URLs were timed. The suspected causes (Sanity fetches at build/revalidation for `/partners/` and `/audit/`, Cloudflare→Vercel hop) are hypotheses — no Vercel function/edge timing, no `server-timing` breakdown, no correlation of slow runs with cache MISS/STALE or revalidation. Draken agrees (his reply §5 gate 6: re-measure "from clean, international edge probes (Vercel edge network) before applying code-level changes"). Urgency is low: GSC is healthy (2,694 impressions 12–24 Nov, +39.6%/day, position 17.8 → 14.7).

**What the re-measurement must establish (agreed protocol, before any code change).** Probes from at least two clean networks (not the audit VM — e.g. Draken's desktop/residential connection plus Vercel edge probes), in at least two geographies (US-East near the `iad1` origin, and one Tier-1 audience region — UK/EU; Asia/Dhaka optional). Minimum 10 runs per URL, spread across times of day. Pages: `/`, `/partners/`, `/audit/`, one blog post, one `/services/` page as control — the same set as the audit, so results are comparable. Per-run data: full `curl -w` timing breakdown (DNS, TCP, TLS, TTFB, total); `x-vercel-cache` (HIT/MISS/STALE), `Age`, `x-vercel-id` region, `cf-cache-status`, `cf-ray` colo; and a same-network control fetch (e.g. example.com or another Vercel site). Hop isolation: compare via-Cloudflare vs direct-to-Vercel timing where possible, and pull Vercel function/edge timing to test the Cloudflare→Vercel hop hypothesis and the Sanity-revalidation hypothesis — specifically whether slow runs correlate with revalidation events. **Decision rule (proposed, to agree with Draken now, not after measuring — the audit states no threshold):** a code change is justified only if server-side TTFB (network baseline subtracted) shows a median above ~0.8 s on cache HITs, or a p95 above ~2 s, or the >2× run-to-run variance reproduces off the VM. If clean-network runs come back fast and stable, P-F1 closes as a VM artifact with no code change.

**Risks of changing code now on VM-only numbers.** Optimising the wrong layer: bundle-splitting (H7/P-F2) or RSC trimming (M2/P-F3) cannot fix routing or revalidation variance. Unverifiable work: with no Lighthouse/PSI/CrUX baseline there is no before/after to prove improvement. Regression risk during an update window: the December core update is rolling out since 24 Nov on a site whose GSC is currently healthy.

**Question for Draken's side.** Can you run the re-measurement from your desktop/residential network (and/or Vercel edge probes) with the protocol above — 10+ runs each on `/`, `/partners/`, `/audit/`, one blog post and one service page, with full timing breakdowns plus `x-vercel-cache`/`Age`/`x-vercel-id` per run — and pull Vercel function/edge timing to test whether slow runs correlate with revalidation or with the Cloudflare→Vercel hop? And do you agree the decision rule: code changes only if server-side TTFB median exceeds ~0.8 s or p95 exceeds ~2 s on cache HITs off the VM, or the >2× variance reproduces — otherwise P-F1 closes as a VM artifact?
